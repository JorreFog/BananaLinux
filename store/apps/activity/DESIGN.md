# Activity — the design it follows

**Status: implemented.** The app is `banana-activity.cpp` plus the baked font
`activity-font.h`, built to the static aarch64 `banana-activity` in this folder. README.md has
the build, the install, the data formats and the controls; `mockups/app-*.png` are the app's own
renders. This document is the visual system it follows, and why each screen looks the way it
does — useful when changing it.

The design follows the menu's own language: the ROCKNIXDS Pixel look as drawn by
`ui/rnds/RndsUI.cpp` and `ui/rnds/RndsRaster.cpp`, with the palette from
`ui/src/settings_pal.cpp` and the accent table from `ui/rnds/RndsUI.cpp`.

**Previews:** `mockups/00-overview.png` (the design study: Library and Timeline, both screens),
plus `library-*`, `timeline-*` at 640×480, light, and 1024×768 (RGBA DS Plus, 1.6×). They are
generated by `mockups/render.py` with the repo's Pixelify Sans and the exact palette/shadows/
radii below.

---

## 1. What the previous build did (and what changed)

The build this replaces (`glyph5x7`, still in the device's old binary) drew in a different
*material* from the menu:

| | previous build |
|---|---|
| Text | a built-in 5×7 bitmap font (`glyph5x7`), upscaled; no FreeType, no TTF |
| Look | flat `box()` fills, no rounded corners, no bands, no dither, no shadows |
| Colour | hard-coded; no `theme`, `accent` or `settings.conf` string in the binary |
| Brand | a 16×14 ASCII banana (`BANANA_SPRITE`) drawn in letters |
| Layout | 640×480 with a `--size 1024x768` scale; title bar "BANANA ACTIVITY LOG — …" |
| Data | `banana/playstats.tsv`, `activity_snapshot.tsv`, `activity_log.tsv` |
| Views | Library (games list, X system, Y sort, dusty 30 d+) and Timeline (left/right by day) |

Three things make the menu look like itself, and that build had none of them:

1. **The sheet.** A tinted, rounded panel (`604×406`) floating on the screen, with a bright
   3 px edge, a light band along the top and a dark inset at the bottom — every menu screen is
   built around one.
2. **Bands + dither.** Surfaces are never flat: a 4×4 dot tile and hard-stop gradient bands
   (a lighter top band, a darker bottom) give the "printed pixel" feel. That is what reads as
   native at a glance.
3. **Pixelify Sans + the type scale**, with wide-tracked uppercase micro-labels.

The new build has all three, plus the third view (TRENDS) that makes the totals mean something.

| Part | Recipe |

| Card / row | r12; border 3 `line` (3 `edge` when selected); bands 0–6 `panelBand`, 6→ `panelBody`; inset `(0,−4)` `panelLow`; outer `(3,3)` black 85% |
| Chip (period, tag) | r8; border 2; band 0–6; active: `accent` fill + `accent.light` border + `#17161c` text |
| Bubble | r12; border 3 `line`; bands 0–10 / 10→; inset `(0,−6)` `bubbleLow`; outer `(4,4)`; 16 px pointer in `line` with a `bubbleBody` inner triangle |
| Key cap | 12 + text wide, 23 high, r4, `kbdBg`; 6 px left inset for the letter |
| Face chip | 40 high, r10, border 3 `edge`; band 0–8 `bubbleBand`; inset `(0,−4)`; outer `(3,3)`; label 19 Medium at 15 px |
| Rail | 5 px wide, r2, `railBg` + dither; thumb 34–40 long, `accent` with a 4 px `accent.light` band, 2 px `edge` border |
| Meter | `meterBg` + 3 px `edge` border; fill `accent`; achievements add 2 px white-45% stripes every 8 px, marching |
| Stats block | values over labels, values `ink`, labels `muted` 13 UPPER ls 1.4; thin `line` 45% divider between columns |

Motion: the menu eases with `easeOut` over 280 ms for entrances (`rise`), 320 ms for pop, and
70 ms per scroll step. Only animate what changes; redraw on input or a data change, not on a
timer (the menu "draws only while something moves").

## 3. The adapted screens

Everything is drawn in the menu's own grid: 640×480 units, status row at y 20–45, sheet at
(18,60) 604×406, face row at y 422, rail at the right edge. The two views keep their current
jobs — Library = "what I play", Timeline = "when I play" — so no feature is lost and the app
still feels like the same tool.

- Period chips are the app's mode (L/R), shown as the active plate the menu uses for START.

## 4. How it is built

`banana-activity.cpp` is one file of plain C++17, no libraries beyond the C++ standard library
and the Linux syscalls it needs. That is deliberate: the binary is static and runs from `/tmp`
with no dependencies, like the previous build, so only the drawing changed.

1. **Text is the real menu font, baked.** `activity-font.h` holds Pixelify Sans rasterised to
   1-bit glyphs at every size the layout asks for (11–70 px), in Regular and Medium, for ASCII
   + Latin-1. `Canvas::text` blits them with per-character advances and letter spacing. No
   FreeType, no TTF at runtime, nothing to fail on the device; `tools/make-font.py` regenerates
   the header from `ui/assets/rnds/fonts`.
2. **Units, not pixels.** Everything is laid out on the menu's 640×480 grid and multiplied by
   `s = panel_width / 640`; borders (`3·s`), radii, shadows and the dither step follow, so the
   Plus (1.6×) is the same design, drawn sharp — the atlas picks the nearest baked size.
3. **The primitives are the menu's**: `fillRound`, `fillRoundRing`, `box(style)` (fill, hard-stop
   bands, dither, inset top/bottom, 3 px border, hard outer shadow), `tri`, and the text
   engine. `BoxStyle` builders (`sheetStyle`, `cardStyle`, `chipStyle`, `bubbleStyle`,
   `faceStyle`, …) carry the recipes from §2, so a screen is written as geometry + styles.
4. **Palette and accent** come from `settings.conf` (`accent = yellow|blue|…`), and the sheet is
   `mix(accent, 34%, #15141a)` exactly as the menu computes it. The timezone in the same file
   is applied to `TZ` before any date is formatted.
5. **Data**: `playstats.tsv` is read; `sessions.tsv` and `snapshot.tsv` are written atomically in
   `banana/activity/`. The views aggregate those sessions per period (totals, days, hours,
   systems, games, longest) in one pass; the deltas run the same pass over the previous window.
   The `NEXT UP` pick and the insight line are pure functions of that aggregate.
6. **No animation, no idle redraw.** The app redraws on input (and when the minute changes), not
   on a timer; a full frame is ~20 ms at 640×480. It is opened for a few seconds, so it costs
   nothing while you look at it.

The one thing it does not do is take the theme's *user* colours/light mode: it draws the dark
palette with the chosen accent. Light mode would mean a second palette pass through every
component; the design tokens are all in one place if that is wanted later.

## 5. Suggestions for the app itself

**In this build:** 1 (NEXT UP and the `Next` sort), 2 (the insight line), 8 (schema + atomic
writes), 10 (share by system) and 11 (the heatmap). The rest is open; 3, 4, 6, 7, 9, 12–20 were
deliberately left out of this version.

Ordered by payoff per hour of work.

### Make it answer a question, not print a table

1. **"What should I play next?"** The app knows the answer: games played once and dropped, games
   untouched for 30+ days (DUSTY already), and long games with little progress. Add one card in
   the overview and a `Y` sort ("Play next") in the list. This is the only screen a player opens
   *before* playing — it deserves a slot next to the totals.
2. **One insight line, generated locally.** "You play most at night", "Pokémon Platinum is 28%
   of your play time", "3 games untouched for a month". No network, no model: thresholds over
   the same data. Rotate it in the sheet's bottom line (where the "LONGEST …" note sits) or as
   the bubble's second line on the overview.
3. **A weekly goal.** A small meter under the hero (e.g. 8 h/week, editable) turns a diary into
   a habit. Use the menu's achievements meter (accent fill + marching stripes) and mark the
   reached state with the accent plate.
4. **Streaks as a 7-dot row.** Current streak, best streak; dots filled in `accent`, today
   outlined. It is one line and it is the most-shared screenshot of every playtime app.
5. **Deltas everywhere.** Every headline number gets "vs previous period" with the same arrow;
   the mockups only show two, but the rule should be uniform (sessions, time, average, active
   days, top system).

### Make the data worth plotting

6. **Store sessions, not plays.** `playstats.tsv` gives plays + total seconds; the log gives
   sessions. Record `start, end, system, rel, seconds, source` and merge plays separated by less
   than ~10 minutes into one session, so "average session" and "time of day" stop being artifacts
   of how often the emulator was closed. Ignore sub-minute sessions (menu taps) unless asked.
7. **Clamp sleep and clock jumps.** A session that spans a suspend/resume or a DST change can be
   9 hours long. Cap at a sane maximum (e.g. 4 h) or split at gaps > 2 min; log the correction.
8. **Schema + atomic writes.** Put a version line at the top of each TSV, write to `.tmp` and
   `rename()` (the menu's `writeAtomic`), skip malformed lines instead of aborting. The log is a
   user's history: a half-written line must never lose it.
9. **Retention.** Keep raw sessions for N days and a daily rollup forever; the current
   `activity_snapshot.tsv` looks like it already does this — make the rollup the source for the
   overview and stop scanning the whole log at launch.

### Give the numbers context

10. **System and genre share** as one horizontal stacked bar (like the time-of-day bar) using
    each system's accent from `systems.cfg`. It is the same "one bar, four tints" idea, and it
    reuses the icons the app already knows how to find.
11. **Heatmap for all time** (7 columns × N weeks, 4 accent steps) under the timeline. It is the
    "all time" view that is actually readable, and it is cheap: one rounded rect per day.
12. **Per-game page (A).** The app's own version of the menu's game page: title, system, first
    and last played, a 12-week histogram, the session list, achievements bar, and a Play action
    (see 13). This is where the per-game data finally gets a home.

### Fit the platform

13. **Launch games from it.** The menu already owns launching; the clean route is a small
    request file (as the menu does for the DS companion) rather than exec'ing emulators
    directly. "Open in the menu's game page" is the low-risk version; "Play" is the good one.
14. **Make it a real tile.** Today it is a Store app with no `catalog.json` entry. Add one
    (`id: activity`, kind `app`, accent `#e8a33d`, summary, `screenshots` from `mockups/`), or
    make it a system app (package + `systems.conf` entry + `/usr/share/banana/apps/activity`),
    like Döda Kvarter and the Store. A place on the shelf is the difference between "found" and
    "not".
15. **The launcher copy is 3 MB per start.** `Activity.sh` copies the binary to `/tmp` every
    run. Skip the copy when the checksum/size matches (or exec from `/data/store/apps/activity`
    directly, as other ports do): it costs a second and SD writes on every open.
16. **Log rotation.** `activity.log` grows forever. Roll at ~256 KB (`.1`), or log only warnings.
17. **Remember the last state** (view, period, filter, sort, selected game) in
    `/data/banana/activity.conf`, and offer "Clear history" in the app (a confirm with A twice,
    like the menu's deletes).

### Craft

18. **Typography discipline.** One hero per screen, labels only in the 11–13 px tracked caps,
    no third size between; ellipsis at the column edge (never wrap a row).
19. **Empty and first-run states.** No data at all should show a short invitation ("Play
    something and come back") inside the sheet, in the menu's muted voice — not an empty chart
    with axes.
20. **Localisation.** The app is English-only; the menu ships `ui/assets/lang/*.tsv`. Even if
    only the UI strings move to a small table, it keeps the door open.
